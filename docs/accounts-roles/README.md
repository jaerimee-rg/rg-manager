# 계정 · 역할 · 초대 체계 — 구현 계획 문서

> **상태: 초안 — 2026-08-30 · 구현 전.** 확정이 필요한 사항은 아래 표와 [01 §9](./01-requirements.md#9-열린-질문) 에 정리했고, 답이 없으면 **권장안**으로 진행한다.
> **요구사항이 세 번에 걸쳐 확정됐다.** ① 같은 카카오 계정으로 관리자·선생님·학부모 각각 가입 ② 로그인은 하나로 하고 **로그인 후 역할 전환**
> ③ **선생님은 관리자가 초대해야 가입**, **학부모는 선생님이 초대해야 그 선생님 이벤트에 신청**, **학부모는 여러 선생님과 연결될 수 있다**.
> 폐기한 "역할별 로그인 페이지 분리" 안은 [01 §10](./01-requirements.md#10-폐기한-대안--역할별-로그인-페이지) 에 기록만 남긴다.

## 한 줄 요약

로그인은 지금처럼 **`/login` 하나(카카오 버튼 하나)**. `users."kakaoId"` 의 단일 UNIQUE 를 **`("kakaoId", role)` 복합 UNIQUE** 로 바꿔 한 사람이 **역할마다 계정 하나씩** 갖고,
로그인 뒤 **역할 전환 메뉴**로 관리자 ↔ 선생님 ↔ 학부모 화면을 카카오 재인증 없이 오간다.
가입은 **초대로만** 열린다 — **선생님은 관리자가 발급한 일회용 초대 링크**, **학부모는 선생님의 초대 링크**. 초대 없이 카카오로 들어온 사람은 계정이 만들어지지 않는다.
학부모는 **여러 선생님과 연결**될 수 있고(`parent_teachers` 다대다), **연결된 선생님의 이벤트만** 보고 신청한다.

## 조직 구조 (2026-08-30 확정)

```
관리자 (1명 — 나)
  └─ 선생님 (여러 명)  ← 관리자가 일회용 초대 링크로만 가입시킨다
        └─ 학부모       ← 선생님이 초대 링크로만 연결한다
              └─ 자녀 = 그 선생님의 students 행

학부모 1명 ── N ── 선생님   (같은 학부모가 여러 선생님과 연결 가능)
한 사람(카카오 계정 1개) = 관리자·선생님·학부모 계정 최대 3개
```

## 현재 시스템에서 출발하는 지점

| 이미 있는 것 | 이번에 하는 일 |
|---|---|
| 로그인 `/login` 하나, 카카오 버튼 하나 | **그대로.** 인가 URL 에 "마지막에 쓰던 역할" 힌트만 붙는다 |
| `users."kakaoId"` UNIQUE → 카카오 계정 하나 = 계정 하나 | **`("kakaoId", role)`** 복합 UNIQUE → 역할마다 행 하나 |
| 카카오 콜백: `state` 없으면 **누구나 선생님 계정 자동 생성**, 초대 토큰이 있으면 학부모 | **초대 없이는 어떤 계정도 만들지 않는다.** 선생님 = 관리자 초대(`teacher_invites`), 학부모 = 선생님 초대(`parent_invites`, 현행) |
| 선생님 카카오 계정이 학부모 초대를 타면 **409 거절** | 학부모 행을 따로 만든다. 선생님이 자기 아이의 학부모도 될 수 있다 |
| 관리자는 관리자 > 사용자의 **역할 편집**(선생님 → 관리자)으로만 생성 | 역할 편집은 남기되, **[관리자 계정 추가]** 로 같은 카카오에 관리자 행을 따로 만든다. 관리자는 1명 전제라 예비 수단 |
| **`parent_accounts.teacherId`** — 학부모 1명 = 선생님 1명 (userId PK) | **`parent_teachers` 다대다.** 학부모가 여러 선생님과 연결. `teacherId` 컬럼은 대표 선생님으로 남겨 두고(호환) 새 코드는 읽지 않는다 |
| `parent_children` 은 소속 선생님을 `parent_accounts` 조인으로 알아낸다 | **`parent_children.teacherId`** 를 명시 컬럼으로. 자녀는 "어느 선생님의 학생인지" 를 스스로 안다 |
| 학부모 일정·사진·신청이 **선생님 1명** 기준(`Event.listUpcomingForParent(teacherId)`) | **연결된 선생님 전체**(`= ANY($1)`) 기준 + 화면에 **선생님 필터** |
| 역할 전환 기능 없음 | `GET/POST /api/auth/roles`, `POST /api/auth/switch-role` + 전환 메뉴 3곳 |

## 핵심 설계 결정 요약

| 항목 | 결정 | 근거 |
|---|---|---|
| 한 사람 = 여러 계정 | **역할마다 `users` 행 하나** (`("kakaoId", role)` UNIQUE). "한 행 + 역할 목록" 은 채택하지 않음 | 학생·수업·이벤트·학부모 소속·로그·JWT 가 전부 `users.id` 로 스코프돼 있다. 행을 나누면 **기존 쿼리·모델·테스트가 거의 그대로**다 |
| 로그인 | `/login` 하나. 콜백이 그 카카오 계정의 행들 중 **마지막에 쓰던 역할** → 없으면 **관리자 > 선생님 > 학부모** 순으로 선택 | 요청 사항. 선택 화면 없이도 전환 메뉴가 한 번 클릭 |
| 가입 | **초대로만.** 선생님 = 관리자의 **일회용** 토큰, 학부모 = 선생님의 **재사용** 링크(현행) | 선생님은 학원 데이터 전체를 갖는 고권한 계정이라 링크가 새면 안 된다 → 1회용·회수 가능. 학부모는 단체 카톡방에 한 번 올리는 운영이라 재사용이 맞다 |
| 초대 없는 카카오 로그인 | 계정을 **만들지 않고** "초대 링크가 필요해요" 안내 | 지금은 아무나 선생님이 된다. 이 구멍을 닫는 것이 이번 변경의 핵심 |
| 학부모 ↔ 선생님 | **다대다** (`parent_teachers`). 학부모는 **연결된 선생님의 이벤트만** 보고 신청 | 형제가 다른 선생님에게 다니거나 학원을 옮기는 경우. "선생님이 초대해야만 그 이벤트에 신청 가능" 을 링크 존재로 강제 |
| 자녀 ↔ 선생님 | 자녀 행(`parent_children`)은 **선생님 1명에 속한다**(`teacherId`). 같은 아이가 두 선생님에게 다니면 **행 2개** | `students` 가 선생님별 명단이라 자녀도 그 단위로 맞춘다. 이름·생년월일 매칭도 그 선생님 명단에서만 |
| 관리자 | **1명 전제**(나). `admin` 비밀번호 계정이 부트스트랩 | 승인 큐·초대 체계를 관리자에게까지 만들 필요가 없다 |
| 역할 전환 | `POST /api/auth/switch-role` — **현재 토큰의 사용자 행이 가진 `kakaoId`** 로만 대상 행을 찾는다 | 본문 값으로 남의 계정에 갈 수 없게 |
| 세션 | 브라우저당 **활성 역할 하나**(토큰 하나). 전환은 교체 | `tokenStorage` 구조를 바꾸지 않는다. 알려진 제한으로 문서화 |
| 하위 호환 | `state` 없음 → 힌트 없음, 디코딩 안 되는 `state` → 옛 학부모 초대 토큰 | 배포 순간에 진행 중이던 로그인·옛 번들이 깨지지 않게 |

| # | 질문 | **확정** |
|---|---|---|
| 1 | "학부모는 선생님이 초대해야만 해당 이벤트에서 신청 가능" — 링크 단위인가, 이벤트 단위인가 | **링크 단위 확정.** *"이벤트는 선생님이 등록한 학부모 아무나 신청 가능합니다."* → 그 선생님과 **연결된 학부모라면 누구나** 그 선생님의 공개 이벤트에 신청한다. 이벤트마다 명단을 지정하지 않는다 ([01 §5.7](./01-requirements.md#57-이벤트-신청-자격-fr-370379)) |
| 2 | 기존 선생님 계정을 그대로 인정할지, 재정비할지 | **재정비 완료.** 운영 DB 의 선생님 계정 중 **이재림 선생님(id 9)만 남기고** 나머지 3개(문아람 · 표혜연 · `카카오_1774927139169`)를 **2026-08-30 삭제**했다. 세 계정 모두 학생·수업·출석·이벤트가 **0건**이라 데이터 손실은 없다. 이후로는 초대로만 가입한다 |
